## Operating boundaries

- **The rule.** Only `checkpoint restore`, its relocation helpers and the absent-root branch of `held_lock` change. L1: archive admission takes `flock(LOCK_EX|LOCK_NB)` on the admitted descriptor before `fstat`, the `realpath` check and the emptiness scan, and `--from` takes the same lock on a no-follow origin descriptor before its clean check; each holds it to the end of the restore. A restore that did not obtain L1 never removes the destination, even one its own `mkdir` created. L2: the marker transaction creates or opens `<origin>/.hexaemeron/lock` no-follow, regular with one link, locks it before reading the root's names and writes `held_lock`'s holder JSON; the marker's allowed set gains `lock` and nothing else. L3: the private stage gets a held `lock` before the fsync and the publishing rename, the active-tree recheck excludes only a root-level regular single-link `lock`, and the capsule and stage snapshots stay strict. L4: a non-init command that finds no state root refuses through the existing missing-state message moved into one shared helper. Every acquisition is non-blocking and every lock descriptor is `O_CLOEXEC`. On every exit the restore unlinks each lock file it created while still holding it. Admission contention refuses as `destination-occupied`; every other contention, and any flock error, refuses through `die("checkpoint restore destination is held by another hexctl command", 1)` before any write. `cmd_checkpoint_restore` stays out of `MUTATING`. `status`, `next` and `verify` stay lock-free. The #1648 anchor, seals and moved-destination sentence stay as they are.

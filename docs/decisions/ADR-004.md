# ADR-004: Safety-layer cluster operational boundaries

## Status

Accepted, 2026-08-19.

## Context

The Hexaemeron Fiat delivery pipeline passes through five phases: `study`,
`runbook`, `implement`, `audit`, and `receipt`. Each phase has a canonical
skill that gates it. Four of those gates -- protasis, elenchus, metron, and
phylax -- operate as a safety cluster around the `implement` phase, preventing
the same classes of failure repeatedly. This record captures their operational
boundaries, handoff rules, and how each skill prevents a specific failure
class as a single decision so new contributors and external tooling do not
have to re-derive them from individual SKILL.md files.

## Decision

### Protasis: the spec gate

Protasis owns the content contract for `study` and `runbook` before any code
is written. It refuses four things: a runbook without a study, an
implementation without a runbook, a study without a testable criterion, and
an assumption buried instead of listed on the page. It forces one literal
question per ambiguity rather than resolving silently.

The spec gate prevents a single failure class: silent assumptions. When the
study carries an unstated constraint, the implementation satisfies a
requirement nobody agreed on and the audit loop discovers the gap.
Protasis blocks this by forcing every assumption onto the page before
the first line of code. The cost of a wrong assumption is a sentence at
the study gate; the cost of a buried one is a full step rework.

The boundary is narrow. Protasis decides what `study.md` and `runbook.md`
must answer. It does not own what gets built. The controller (`fiat`) runs
the study and runbook phases under this contract. `hypomnema` records the
decisions after they are made by this gate.

Protasis has no mechanical subset. Its checks are read against a study
document by a reviewer, not enforced by a script. The only defense after
the gate is the audit loop.

### Elenchus: the root-cause gate

Elenchus works a failure that has already happened. It stops the line,
reproduces the failure, localises the layer, reduces to a minimal case,
fixes the mechanism, and guards with a test that fails on the old code.
It refuses three things: a fix without reproduction, a guard without a
failing test, and a resume with still-red test suites.

The root-cause gate prevents one failure class: fixing without guarding.
A bug fixed without a test that fails on the old code returns when the
tree moves. Elenchus blocks this by requiring every fix to carry a guard
test that was seen red on the unfixed tree. A red test suite with a
uncommitted fix exits the step entirely.

The boundary is narrow. Elenchus owns the cause mechanism, not the
location. A fix must address the mechanism. `elemchus` adds temporary
instrumentation and removes it. `ephoros` keeps the telemetry that
survives. `fiat` has no counterpart for this work.

`elemchus.py` implements the mechanical subset. It reports guarded,
unguarded, passed, or inconclusive for each commit's guard test. The
report exits 0, but the guard test itself must fail on the parent.

### Metron: the performance gate

Metron owns every performance measurement except Solidity gas. It changes
only against a recorded baseline, keeps only what beats the noise, and
reverts everything else. It refuses four things: a performance edit with
no before, a keep with no re-measurement, a neutral that costs forever,
and a red-suite regression in a win's clothing.

The performance gate prevents one failure class: keeping an unmeasured
change. A performance edit without a recorded baseline is an opinion
with a diff. Metron blocks this by requiring baseline and re-measurement
for every speed change. A neutral result inside run-to-run variance
reverts and the change is maintained forever at full cost.

The boundary is narrow. Metron owns baseline first, one change,
re-measure, keep-or-revert. It does not own what makes something slow.
`ephoros` emits the signals. `hermes` owns Solidity gas through Foundry.
`elenchus` owns broken code, not slow code.

Metron has one mechanical subset: the attempt ledger. Every benchmark --
kept or reverted -- is recorded there so the same dead idea does not
return next quarter. The ledger lives beside the code a reviewer reads.

### Phylax: the off-chain gate

Phylax owns the off-chain surface where data enters the process: Python
tooling, a TypeScript application, and a long-running service. It names
boundaries first, runs STRIDE across each, and enforces four settled rules
through a parser: validate external data, pass subprocess arguments as a
list, pin dependencies, keep credentials out of source.

The off-chain gate prevents one failure class: unvalidated input at an
unnamed boundary. An RPC response, a venue record, a downloaded archive,
and a model reply are all hostile until checked at the line. Phylax blocks
this by running `phylax.py` over every touched path and requiring exit 0.
A boundary that nobody names is a boundary that carries no control.

The boundary is narrow. Phylax owns everything from outside the process.
It does not own contracts or on-chain proof. `solidity-auditor` and
`x-ray` review contracts. `elenchus` works a failure that already
happened. The off-chain surface is the boundary; on-chain audit is
separate.

`phylax.py` implements the mechanical subset. It reports shell
invocations, subprocess strings, unpinned dependencies, and credential
leaks. Exit 0 is required. Deliberate exceptions state a reason in a
`# phylax: allow <why>` pragma.

### How they interact

These four skills form a sequence around implementation. Protasis gates
before the first line of code. Elenchus and phylax operate in parallel
during and after implementation. Metron gates on performance after a
change lands. The handoff from one to another is a failure condition
rather than a transfer: a fix without a guard exits elenchus, a
hardened boundary without a test exits phylax, a perf win without a
baseline exits metron, and a step without a runbook exits protasis.
Each skill's mechanical subset reports its boundary, but the report
does not close the loop -- a written test does.

### Why this cluster, not others

The remaining first-party skills -- `fiat`, `hypomnema`, `imprimatur`,
`vulgate`, `ephoros`, and `kronos` -- do not share the failure-prevention
mandate of the cluster. `fiat` is an orchestrator, `hypomnema` records
after the fact, `imprimatur` and `vulgate` are prose quality, `ephoros`
decides signals, and `kronos` is terminal and excludes itself. The
cluster is defined by a shared property: each skill refuses a class of
action that would introduce a failure into the tree.

### Alternatives

1. **Merge all four into a single safety skill.** Would simplify
   invocation but collapses four distinct failure classes under one
   name. Each mechanical subset would need to be conditional on
   which domain applies, and the audit loop would lose the ability
   to gate differently on spec versus hardening versus perf.

2. **Place all four under fiat's contract.** Would make fiat
   responsible for every phase gate including spec, root-cause, and
   perf gates. Fiat already carries artefact paths and receipt
   commands; adding four more refusal rules dilutes the controller
   role that the audit loop depends on.

3. **Add `x-ray`, `solidity-auditor`, and `fizz` to the cluster.**
   They cover the on-chain half and already form the three Pashov
   skills vendored under Hexaemeron. The cluster here covers only
   off-chain and pre-implementation gates. On-chain audit has its
   own loop under `fiat` with its own safety rules.

## Consequences

- A contributor must read four SKILL.md files in addition to ADR-004
  to understand the safety cluster. The ADR replaces reading them for
  high-level scope, not for operational detail.
- Adding a new safety gate requires deciding which existing skill it
  hands off to. The cluster boundary is fixed; new entries expand it.
- The mechanical subsets for elenchus and phylax run from CI as exit
  criteria for the `implement` phase. Neither can be bypassed by audit
  round.
- Protasis leaves no receipt from a script. Its checks are read against
  a study document by a reviewer. A study can pass the checklist and
  still contain a buried assumption. The audit loop is the remaining
  defense.

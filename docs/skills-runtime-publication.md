# Publishing the skills runtime

`wildcat-finance/skills-runtime` holds the installable package. Every file in it
is generated by `scripts/portable_promise_machine.py` in this repository, and an
edit made there is overwritten by the next rebuild.

## What runs, and where

The destination holds one scheduled workflow. It clones this repository over a
literal public URL, regenerates the package, verifies it, and commits only when
the bytes changed. It runs hourly and on manual dispatch, and it is guarded so
it runs in `wildcat-finance/skills-runtime` and nowhere else.

The job uses its own `GITHUB_TOKEN` with `contents: write`. It needs no other
scope and no stored secret, because it writes to the repository it runs in
rather than pushing across a boundary. That is the whole reason the job runs in
the destination rather than here.

## Why the workflow cannot update itself

GitHub refuses any push that creates or updates a file under
`.github/workflows/` unless the token holds the Workflows permission, and
`GITHUB_TOKEN` can never hold it. The job therefore cannot rewrite its own
definition, which is a property worth keeping: a compromised generation step
cannot widen what runs next.

The consequence is that a change to the workflow does not reach the destination
on its own. Its canonical copy is `distribution/skills-runtime/sync.yml` here,
and somebody holding `workflow` scope has to push the updated file to the
destination. The job compares the two on every run and fails when they differ,
so a forgotten push is loud rather than silent.

## Bootstrapping from nothing

Given an empty destination repository:

```bash
git clone https://github.com/wildcat-finance/skills-runtime.git
python3 scripts/portable_promise_machine.py package --out /tmp/package
cp -R /tmp/package/. skills-runtime/
mkdir -p skills-runtime/.github/workflows
cp distribution/skills-runtime/sync.yml skills-runtime/.github/workflows/sync.yml
cd skills-runtime && git add -A && git commit && git push
```

The package action replaces the whole output directory, so it refuses one that
is not empty and that it did not write. A fresh clone already holds `.git` and
so is refused: generate into a separate directory and copy the contents across,
which is what the scheduled job does with `RUNNER_TEMP`. Pointing `--out` at the
clone itself would destroy its `.git`.

## Checking that the published package is current

The destination's `README.md` names the exact source commit it was generated
from. Compare it against this repository's `main`:

```bash
gh api repos/wildcat-finance/skills-runtime/contents/README.md \
  --jq '.content' | base64 -d | grep -o '[0-9a-f]\{40\}'
gh api repos/wildcat-finance/skills/commits/main --jq .sha
```

A difference means the destination has not rebuilt since that source commit
landed. Up to an hour of lag is expected and accepted; more than that means the
scheduled job is failing, and its runs are in the destination's Actions tab.

This is the question #836 records as unanswerable for the older marketplace
mirror. Recording the source commit in the artefact is what makes it answerable
here.
